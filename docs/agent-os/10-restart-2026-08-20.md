## 1. Why this document exists

On 2026-07-18 the master plan opened with this thesis:

> HDPM-OS already *detects* everything. What it lacks is *motion*: since July 1 there is exactly one human action in the audit trail.

That was right. In the five weeks since, **263 more commits landed** (169 in July, 94 in August) and the motion number did not move. We kept building capability at full speed past the point where our own document said capability was not the problem.

This restart exists to stop that, on purpose, in writing.

### What the codebase actually looks like now

| | |
|---|---|
| TS/TSX | 90,690 lines |
| API routes | 185 |
| Pages | 29 |
| Vercel crons | 28 |
| Migrations | 64 |
| Strategy doc families | 5 (`agent-os`, `hdpm-os`, `maintenance-os`, `soul-brain`, `demo-site`) — ~60 documents |
| Human actions in the audit trail | ~0–1 / week |

Every number in that table is large except the last one, which is the only one that matters.

### The diagnosis

Two causes, and they compound.

**a) Nothing terminates.** With AppFolio read-only, every agent output ends the same way: here's a problem, here's a draft, now go open AppFolio and type it in. The reward for engaging with the system is more clicking. That is not an adoption problem you can solve with better UI — it is structural. `lib/appfolio.ts` is 55KB and contains exactly one HTTP method: `GET`.

**b) We may have built a team of agents and never turned them on.** Every agent run begins with a guard that reads `agent_config` and returns `L0` — silently — when the row is missing:

```ts
const cfg = await getAgentConfig(MORNING_CARD_AGENT, MORNING_CARD_ACTION);
if (effectiveLevel(cfg) < 2) return { ...result, halted: 'no agent_config row' };
```

The seed rows live in `20260719_agent_config.sql`, which the master plan lists as **"to run in SQL editor"** — a manual step. Four briefs carry that same note. If those migrations never ran, the Phase 1 agent team has been firing as a no-op cron since July 19, logging a line nobody reads.

**Week 0 resolves this before anything else is built.** See §7.

## 2. First principles

Six rules. Everything below is downstream of them.

1. **Motion is the only metric.** Human actions per week in the audit trail. Not exceptions detected, not dashboard views, not features shipped. If the number doesn't move, nothing we did counts.

2. **Nothing ships that doesn't terminate.** If an agent output can't end in an action that *completes* the work, we don't build it. A finding that produces "hmm, look at this" is worse than nothing — it teaches people the system generates homework, and that lesson generalizes to the findings that matter.

3. **Go where they already are.** The best surface is one the person already opens. Cheryl's Outlook drafts folder beats a Slack card beats a dashboard tab. Ranked by behavior change required, ascending.

4. **One loop, one person, at a time.** A system that completely solves one person's day gets talked about at lunch. A system that partially touches seven people's days gets ignored by all seven. We built the second thing. We are now building the first.

5. **Every surface names an owner and a cadence.** Any view, tab, or tripwire without a named person who touches it on a stated rhythm goes dormant. Not deleted — dormant.

6. **Autonomy is earned per action type, never granted.** Inherited unchanged from `00` §2: L0→L4 ladder, promotion only at <5% override across ≥4 weeks, proposed to Craig, never self-granted, never past the Q2 ceilings. Owner- and tenant-facing sends stay hard-walled at L2 permanently.

## 3. What write access actually changes

Craig's framing for this restart was "assume we can add the AppFolio write." Worth being precise about what that buys, because it is not mainly hours.

### The break-even, since it will be asked

AppFolio Max at $1.00/door/month = **$850/mo · $10,200/yr** at 850 doors.

| Labor basis | $/hr | hr/month to break even | hr/week | FTE offset |
|---|---|---|---|---|
| Raw wage | $22.00 | **38.6** | 8.9 | 0.22 |
| Loaded 1.25× | $27.50 | 30.9 | 7.1 | 0.18 |
| Loaded 1.30× | $28.60 | 29.7 | 6.9 | 0.17 |
| Loaded 1.40× | $30.80 | 27.6 | 6.4 | 0.16 |

Roughly **a fifth to a quarter of one FTE**, or about 1.3 hours per person per week across seven office staff. Per door: **2.7 minutes per door per month.**

For scale: 265 of 360 open WOs are coordination-stuck. At three touches each and four minutes a touch, draining that backlog once is ~53 hours. Steady-state coordination at 850 doors plausibly runs 30–50 hr/month. **The maintenance coordination loop alone sits at or above break-even** before counting PM paperwork, inspections, owner comms, or delinquency.

Those are assumptions, not measurements. The payback isn't close enough to need better ones.

### But the real argument isn't hours

Write access is what makes rule #2 possible. Without it, an approval tap is a half-action — the human still has to finish the job in the system of record. With it, the tap *is* the job. Everything about the autonomy ladder is theatre until a tap can complete something on its own.

That is the case for the $850: not labor arbitrage, but the difference between a monitoring tool the team tolerates and an operating system the team relies on.

### Two things to settle before spending

- **Confirm in writing which entities Max makes writable** — work orders specifically. The entire case rests on one sentence in the API tier docs. If Max opens tenants and leases but not WOs, the math collapses.
- **Call Haven first.** Haven already writes work orders into AppFolio at partner level despite us being on Plus. Ask whether they'll expose write-through for our own automation. That call might save $10,200/yr.

And budget the build: the client is `GET`-only today. Max starts a clock, it doesn't flip a switch.

## 4. Loop 1 — Cheryl's estimate chase

**One loop. This one. Nothing else new until it clears the gate.**

### Why this one

| Criterion | Why the estimate chase wins |
|---|---|
| Real money, standing still | ~100 WOs stuck in estimate states, median 24 business days (~35 calendar), max 144 days |
| Work she already hates | Chasing vendors for bids. Nobody at HDPM will miss this. |
| Zero new surface | Delivery is her Outlook drafts folder — a place she opens every day already |
| Already built | Brief D shipped 2026-07-19; Azure app-only `Mail.ReadWrite` registered and policy-scoped to `cheryl@` + `info@` |
| Terminates cleanly | She hits send. The action is complete. Nothing to re-type into AppFolio. |

That last row is the whole point. **The estimate chase is the one loop that already satisfies rule #2 without write access.** Which is why it goes first, and why it goes alone.

### The loop

```
TW11 pool (status-age proxy, >3 business days in Estimate Requested / Estimated)
    │
    ├─ dedupe against agent_outbox — never chase the same vendor inside 3 business days
    │
    ▼
Estimate Chaser drafts the email  ─────►  Cheryl's Outlook drafts folder
                                              │
                                              ▼
                                    She reads it, hits send
                                              │
                                              ▼
                          agent_proposal → approved · wo_event → actor: cheryl
                                              │
                                              ▼
                                    The number moves
```

Constraints inherited from Session A: **no dollar amounts exist in any reachable API**, so chase language never claims an amount. Escalation: anything chased 3× or aged >45d rolls into Craig's Ops Brief as a "needs Craig" item.

### What is explicitly NOT in Loop 1

The Morning Action Card. It's built, it's cron-wired, and it stays off until the chase clears the gate.

This is the sharpest departure from the July plan, which launched the card, the chaser, and the brief together. The reasoning: **the card is a new place to look; the drafts folder is not.** If motion is the problem, the first intervention should require zero behavior change. Prove she'll act when acting costs nothing, then earn the right to ask her to open something.

**Exception, deliberate:** Craig's Ops Brief (#7) stays on. It's self-addressed, L3, costs no one any attention but Craig's, and it is how we watch the number. It is not a Loop 1 surface; it is the instrument.

## 5. The interaction model

From the Viktor teardown, applied. These govern every agent surface from here on.

**One persona, one `@name`.** One Slack app, one bot identity, one place to talk. The multi-agent structure is real and lives in the backend; staff never learn a routing table. Attribution rides in the message, not in the sender.

**Every message carries a "why" line.** Not just what happened — why this person is being told, now.

```
Dez — Firkus hasn't scheduled the Wilson unit in 61 days.
Draft chase below.        [Send]  [Edit]  [Not now]
— maintenance watch · WO #4471 · 3rd chase · [stop these]
```

**One item per thread.** Proactive messages open a thread; the subagent owning that item handles replies there with its context loaded. Staff experience it as "the conversation about the Wilson unit," not "talking to bot #3."

**Quiet by default.** One nudge maximum, ever. Every message carries a one-tap "stop these." Adoption respects annoyance.

**Cap the ask.** When the Morning Card earns its way in, it caps at **seven items** — not 205 exceptions. Finishing must be achievable. "You cleared 7/7, backlog down 4% this week" beats any dashboard.

## 7. Sequence

### Week 0 — Verify before building (Craig, ~1 hour)

Nothing is built until these four questions have answers.

1. **Did the migrations run?**
   ```sql
   select agent, action_type, autonomy_level, enabled from agent_config order by agent;
   ```
   Empty or erroring = the agent team has been a no-op since July 19, and §1(b) is the whole story. Also check `metrics_snapshot`, `agent_proposal`, `agent_outbox`.

2. **Is the baseline frozen?** If `metrics_snapshot` never ran, the before/after case study has no *before*. Freeze it now — it must predate any agent going live.

3. **TW11 ownership.** Confirm `lib/maintenance/tripwires.ts` routes the estimate pool to **Cheryl**, not Jen. Brief A claims the fix; verify it landed. Enabling digests before this mails 78 stuck WOs to someone on leave.

4. **Vendor email extraction.** ~99% of vendors have emails in AppFolio; `extractEmail()` misses them. Run `/api/agents/vendor-contact-audit`, find the real field, fix it. **The chaser cannot chase anyone until this works** — this is Loop 1's one hard blocker.

### Weeks 1–2 — Loop 1 live

- Enable `estimate_chaser / vendor_chase` at **L1** in `agent_config`. Nothing else enabled.
- First run staged with `AGENT_GRAPH_DRYRUN=1`; Craig reads the drafts before Cheryl sees any.
- Sit with Cheryl for 20 minutes on day 1. Not a demo — watch her open the folder and read a draft, and fix the language she stumbles on.
- Ops Brief on, to Craig only. Matt offered.

### Weeks 3–6 — Measure, then decide

- Weekly: sends, edit rate, and what she changed. **Edits are the signal** — they are the training data for promotion and the fastest read on whether the drafts are any good.
- If the gate clears: Loop 2 is the **Morning Action Card**, capped at seven, Slack with an email mirror. One loop, again.
- If the gate doesn't clear: §8.

### Sep 4 — Write path

Bring three things: the motion number, the retyped-touch count from `wo_event`, and AppFolio MCP specs. The decision stays three-way — **Write API ($850/mo) vs. the anticipated MCP vs. keep retyping** — with ≥40 retyped touches/week as the threshold that makes the Write API pay for itself in retyping labor alone.

## 8. The one number, and when we stop

**The number:** agent-originated actions completed by a human, per week.
`agent_proposal.status ∈ (approved, edited)` + corresponding `wo_event` rows with a human actor.

**Baseline:** ~0–1/week.

**Loop 1 gate:** **≥15 sends/week for two consecutive weeks**, and Cheryl says "keep it" out loud, unprompted.

**Kill criterion:** if Loop 1 has not cleared the gate by **2026-10-01**, we stop building agents. Not "try Loop 2." Not "improve the drafts." Stop, and revisit whether HDPM's constraint is software at all — it may be vendor capacity (Firkus: 46 WOs, median 95 days against ~10–13 for every other major vendor), in which case the answer is the Bend Radiant acquisition, not an agent.

Writing down a real stop condition is what separates this from more optimism. Six weeks, one number, a date.

## 9. What we are explicitly not doing

- No new detection. Twelve tripwires and 205 exceptions is already more than the team can act on.
- No new dashboard views, tabs, or panels.
- No second Slack bot. One persona, always.
- No agents for Alberto, Penny, Brody, Ashley, or the PM lane until Loop 1 clears. Their agents are designed in `00` §3 and stay designed.
- No Email Triage, no Intake Triage, no reconciliation, no inspections cadence, no SMS day-close — all queued behind the gate.
- No multi-tenant, billing, or productization work. The `org_id`/RLS seams already in place are sufficient; everything else waits for a design partner.
- **No new strategy documents.** This is the last one until the gate resolves.
